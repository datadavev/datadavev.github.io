DOIs are Borken. Sort of.

Unpredictable results when resolving DOIs.

data
identifiers

The current DataCite DOI resolver services does not respect content negotiation for JSON-LD. Instead of returning the location of the requested resource, the location of DataCite specific content is returned. The consequence is that the DataCite DOI infrastructure will not reliably resolve JSON-LD resources.

The problem

Implementation of content negotiation by DOI resolver implementations can override the functionality of a resource provider creating unpredictable results for a resource consumer.

For example, the DOI 10.1594/PANGAEA.930327 identifies a resource located at the URL https://doi.pangaea.de/10.1594/PANGAEA.930327. Requesting this resource over HTTP using an Accept header preferring text/html results in the HTML representation of the resource. When requesting the resource from that URL with a preference of application/ld+json, the resource provider returns a JSON-LD representation of the resource. This is the expected behavior.

If however a resource consumer performs DOI resolution to determine the location of the resource then the behavior is different. The DOI resolver will instead present the location of the resolver implementation copy of metadata (e.g. DataCite metadata). This means DOIs can not be used to reliably reference some content types. The list of content types overridden by DataCite includes:

Format Content Type
RDF XML application/rdf+xml
RDF Turtle text/turtle
Citeproc JSON application/vnd.citationstyles.csl+json
Schema.org in JSON-LD application/ld+json
Codemeta application/vnd.codemeta.ld+json
Formatted text citation text/x-bibliography
RIS application/x-research-info-systems
BibTeX application/x-bibtex
DataCite XML application/vnd.datacite.datacite+xml
DataCite JSON application/vnd.datacite.datacite+json
JATS application/vnd.jats+xml

Example

The following example illustrates the issue for the case of JSON-LD (a common serialization of schema.org RDF).

A request to resolve the HTML representation behaves as expected (> and < denote request and response respectively):

> https://doi.org/10.1594/PANGAEA.930327 
> Accept: text/html
< 302 
< Location: https://doi.pangaea.de/10.1594/PANGAEA.930327

> https://doi.pangaea.de/10.1594/PANGAEA.930327 
> Accept: text/html
< 200 
< Content-Type: text/html

A request for the JSON-LD representation however results in a different resource than the copy returned by the resource authority. Request JSON-LD directly from the resource provider:

> https://doi.pangaea.de/10.1594/PANGAEA.930327 
> Accept: application/ld+json
< 200 
< Content-Type: application/ld+json; charset=UTF-8

Request JSON-LD by way of DOI resolution:

> https://doi.org/10.1594/PANGAEA.930327 
> Accept: application/ld+json
< 302 
< Location: https://data.crosscite.org/10.1594%2FPANGAEA.930327

> https://data.crosscite.org/10.1594%2FPANGAEA.930327 
> Accept: application/ld+json
< 200 
< Content-Type: application/ld+json

Note that the final URL returned by the resolver is different to the URL presented by the resource owner.

There are significant differences in the JSON-LD retrieved from the resource provider compared with the DOI service. See below.

Besides the impact on reliable retrieval of authoritative content representations, this behavior also blocks information such as accesses to the resource that may useful to the resource provider for metrics collation and so forth.

Suggested fix

The DOI resolver service should respond with a resolver service metadata content representation only when specifically requested.

RFC 8288 provides a mechanism for advertising the availablity of related resource, including alternate representations of a resource aligned with different profiles.

Web Linking defines a model for the relationships between resources on the Web (“links”) and the type of those relationships (“link relation types”).

The resolver can advertise an alternate representation of a resource by including such information in the HTTP response Link header. Similarly, a resource provider could also promote availability of the resolver metadata by presenting the location of such a representation in its response.

At a minimum such information should be included when a resolver returns an alternate representation of a resource not specifically presented by the resource authority.

Ideally, the DOI resolver should only respond with information about the location of the requested resource.

For example the DOI resolver could respond similarly to the following example, with the redirect response including a link to the location of the resolver metadata:

> https://doi.org/10.1594/PANGAEA.930327 Accept:application/ld+json
< Link: <https://data.crosscite.org/10.1594%2FPANGAEA.930327>; rel="alternate"; type="application/ld+json"; profile="http://datacite.org/schema"
< 302 https://doi.pangaea.de/10.1594/PANGAEA.930327

> https://doi.pangaea.de/10.1594/PANGAEA.930327 Accept:application/ld+json
< 200 application/ld+json

Note however that link header handling in redirect responses would only be available to programmatic clients. Intermediate communication details are not exposed to web browser based clients.
